# Redis matchmaking

## 1. Контекст и проблема

`MemoryRepository` работает по принципу блокирования mutex перед выполнением критической секции.
То есть перед началом работы с внутренней структурой данных мы умышленно блокируем mutex и выполняем критическую секцию, что позволяет нам безопасно обработать получение/удаление партнера из репозитория, не опасаясь того, что другая goroutine может в этот момент получить некорректные данные, так как другая goroutine попросту не может работать с этими данными параллельно с текущей, заблокировавшей mutex.

Mutex помогает избежать гонки данных в рамках одного инстанса, но при наличии нескольких запущенных экземпляров мы получаем ряд проблем:
1) у каждого процесса собственная память;
2) у каждого процесса собственный mutex;
3) mutex backend-1 ничего не блокирует в backend-2.

То есть, чтобы работать в рамках нескольких серверов нам потребуется какой-то инструмент, который позволяет хранить данные и обеспечивать к ним атомарный доступ для чтения/записи.
Но самих по себе атомарных операций недостаточно, атомарной должна быть вся бизнес-операция следующего вида:
1) проверить состояние клиента;
2) найти партнера
3) удалить партнера или добавить клиента
4) вернуть результат.

На текущий момент приложение запускается в одном инстансе, в таком случае конфликтов не возникает и блокировка mutex обеспечивает атомарность операций.
В случае старта новых инстансов с использованием Redis, но без атомарности операции, мы уже получаем ту самую логическую race condition связанную с получением одного и того же партнера, до того, как функция уберет его из очереди. Так же партнер уже может отменить поиск на своей стороне, но все равно попасть в выдачу, потому что его получение из структуры данных произошло раньше его удаления из этой структуры.

Алгоритм с проблемой:
```
backend-1: прочитал partner-X
backend-2: прочитал partner-X
backend-1: удалил partner-X
backend-2: попытался удалить partner-X
```

## 2. Инварианты

Система должна гарантировать, что:
1) один ClientID может иметь не более одного активного поиска и находиться не более чем в одной очереди;
2) при повторном запросе к матчмейкингу с той же языковой парой, мы оставим клиента в очереди на том же самом месте, то есть его позиция никак не поменяется;
3) повторный запрос с другой языковой парой отклоняется, а существующая запись и позиция клиента не изменяются;
4) среди совместимых ожидающих пользователей выбирается пользователь, который раньше остальных вошёл в соответствующую очередь;
5) один ожидающий пользователь может быть извлечён из очереди и включен не более чем в один `match`;
6) для каждого `ClientID` в очереди существуют данные, достаточные для восстановления соответствующего `WaitingUser`;
7) запись пользователя без членства в очереди также не должна оставаться после завершённой операции.

## 3. Redis data model

### 3.1. Требуемые данные

`WaitingUser`
Структура необходима для хранения сопоставления идентификатора клиента с языковой парой, по которой он сделал запрос на поиск партнера.

Логические поля:

- `client_id` - хранит строковое представление идентификатора клиента;
- `native_language_code` - хранит код языка, который знает клиент;
- `learning_language_code` - хранит код языка, который клиент хочет выучить.

Для восстановления `WaitingUser` логически нужны три значения. Физически в элементе очереди хранится только `client_id`, а языковые коды выводятся из `key` направленной очереди.
После чтения из Redis значения не считаются валидными автоматически. Адаптер
последовательно восстанавливает их через `NewClientID`, `NewLanguage`,
`NewLanguagePair` и `NewWaitingUser`.

Для каждой языковой пары мы можем организовать свою очередь, это даст нам возможность получать коды языков прямо из ключа очереди.
Ключи могут быть такого формата:
`matchmaking:queue:{native_language}:{learning_language}`.

Примеры ключей:
`matchmaking:queue:ru:en`
`matchmaking:queue:en:ru`

А внутри самой очереди будут хранится только лишь `client_id`.

Порядок ожидания не является полем `WaitingUser`: он хранится положением `client_id` внутри упорядоченной структуры `Redis`.

Мы не будем сохранять ту же структуру полей, которую используем в domain-модели, потому что:
- закрытые поля domain-структуры не являются persistence-контрактом;
- внутреннее устройство Go-типа может измениться;
- данные должны восстанавливаться через конструкторы с повторной валидацией.

Имея только `ClientID`, метод `RemoveFromQueue` не знает key очереди. Поэтому потребуется обратный индекс:
`client_id` → направленная языковая пара или `key` очереди.

### 3.2. Ключи и структуры данных

| Key pattern | Redis type | Содержимое | Назначение |
|---|---|---|---|
| `fluent-swap:queue:{native}:{learning}` | LIST | `client_id` | Хранение и получение `client_id` в порядке очереди |
| `fluent-swap:queue:index:clients` | HASH | `client_id -> fluent-swap:queue:ru:en` | По индексу мы сразу получим ключ очереди, в которой находится клиент, для последующего удаления его из очереди |

#### Очереди по языковому ключу

Структура `LIST` позволит нам класть идентификаторы в начало структуры и получать с конца списка. С ее помощью мы реализуем логику очереди. Вот пример подобного процесса с сайта официальной документации:
```
redis> LPUSH fluent-swap:queue:ru:en 3431-fdf-31345-drfgfgg
(integer) 1
redis> LPUSH fluent-swap:queue:ru:en 5432-fdw-24345-drfgllm
(integer) 2
redis> RPOP fluent-swap:queue:ru:en
"3431-fdf-31345-drfgfgg"
redis> RPOP fluent-swap:queue:ru:en
"5432-fdw-24345-drfgllm"
redis> 

```

`LPUSH` - добавляет слева
`RPOP` - извлекает справа

Для удаления из структуры `LIST` можно будет воспользоваться функцией `LREM`:
```
LREM key count element — удаляет из списка элементы, равные значению element.count > 0: удаляет первые count вхождений от начала к концу.
count < 0: удаляет первые abs(count) вхождений от конца к началу.
count = 0: удаляет все вхождения элемента.

Пример: LREM fluent-swap:queue:ru:en 0 "3431-fdf-31345-drfgfgg" (удалит все строки "3431-fdf-31345-drfgfgg" из списка fluent-swap:queue:ru:en).
```

Почему `LIST`?
- `LIST` естественно сохраняет порядок;
- операции на концах эффективны;
- `LREM` для произвольного удаления имеет линейную сложность;
- `LIST` самостоятельно не обеспечивает уникальность;
- для ожидаемого размера очереди V1 этот компромисс принимается.

`ZSET` позволяет эффективно удалять произвольного пользователя и обеспечивает уникальность member внутри одной очереди, но требует отдельно формировать score для FIFO. Для небольших очередей V1 выбран более простой `LIST`, несмотря на линейную сложность `LREM`.

#### Обратный индекс клиентов

`HASH` с ключом `fluent-swap:queue:index:clients` используется как обратный
индекс. Полем является `client_id`, а значением Redis key очереди, в которой
находится клиент.

Пример:

```text
HSET fluent-swap:queue:index:clients client-123 fluent-swap:queue:ru:en
HGET fluent-swap:queue:index:clients client-123
fluent-swap:queue:ru:en
```

`HASH` только позволяет быстро найти состояние клиента, но сам по себе не обеспечивает атомарность. Изменение `LIST` и `HASH` должно выполняться одной атомарной операцией. Иначе возможны рассинхронизации:
- клиент есть в `LIST`, но отсутствует в `HASH`;
- клиент есть в `HASH`, но отсутствует в `LIST`.

Общий `HASH` выбран потому, что он хранит весь обратный индекс под одним Redis key и позволяет получать, создавать и удалять связь по `client_id` через `HGET`, `HSET` и `HDEL`. Альтернатива - отдельный `STRING` key на каждого клиента - упростила бы независимый TTL, но увеличила бы количество ключей.

TTL применяется ко всему `HASH`, а не к отдельному полю клиента. Поэтому общий `HASH` не поддерживает независимый TTL для каждого ожидающего пользователя.
