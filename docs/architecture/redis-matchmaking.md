# Redis matchmaking

## 1. Контекст и проблема

`MemoryRepository` работает по принципу блокирования mutex перед выполнением критической секции.
То есть перед началом работы с внутренней структурой данных мы умышленно блокируем mutex и выполняем критическую секцию, что позволяет нам безопасно обработать получение/удаление партнера из репозитория, не опасаясь того, что другая goroutine может в этот момент получить некорректные данные, так как другая goroutine попросту не может работать с этими данными параллельно с текущей, заблокировавшей mutex.

Mutex помогает избежать гонки данных в рамках одного инстанса, но при наличии нескольких запущенных экземпляров мы получаем ряд проблем:
1) у каждого процесса собственная память;
2) у каждого процесса собственный mutex;
3) mutex backend-1 ничего не блокирует в backend-2.

То есть, чтобы работать в рамках нескольких серверов нам потребуется какой-то инструмент, который позволяет хранить данные и обеспечивать к ним атомарный доступ для чтения/записи.
Но самих по себе атомарных операций недостаточно, атомарной должна быть вся бизнес-операция следующего вида:
1) проверить состояние клиента;
2) найти партнера
3) удалить партнера или добавить клиента
4) вернуть результат.

На текущий момент приложение запускается в одном инстансе, в таком случае конфликтов не возникает и блокировка mutex обеспечивает атомарность операций.
В случае старта новых инстансов с использованием Redis, но без атомарности операции, мы уже получаем ту самую логическую race condition связанную с получением одного и того же партнера, до того, как функция уберет его из очереди. Так же партнер уже может отменить поиск на своей стороне, но все равно попасть в выдачу, потому что его получение из структуры данных произошло раньше его удаления из этой структуры.

Алгоритм с проблемой:
```
backend-1: прочитал partner-X
backend-2: прочитал partner-X
backend-1: удалил partner-X
backend-2: попытался удалить partner-X
```

## 2. Инварианты

Система должна гарантировать, что:
1) один ClientID может иметь не более одного активного поиска и находиться не более чем в одной очереди;
2) при повторном запросе к матчмейкингу с той же языковой парой, мы оставим клиента в очереди на том же самом месте, то есть его позиция никак не поменяется;
3) повторный запрос с другой языковой парой отклоняется, а существующая запись и позиция клиента не изменяются;
4) среди совместимых ожидающих пользователей выбирается пользователь, который раньше остальных вошёл в соответствующую очередь;
5) один ожидающий пользователь может быть извлечён из очереди и включен не более чем в один `match`;
6) для каждого `ClientID` в очереди существуют данные, достаточные для восстановления соответствующего `WaitingUser`;
7) запись пользователя без членства в очереди также не должна оставаться после завершённой операции.

## 3. Redis data model

### 3.1. Требуемые данные

`WaitingUser`
Структура необходима для хранения сопоставления идентификатора клиента с языковой парой, по которой он сделал запрос на поиск партнера.

Логические поля:

- `client_id` - хранит строковое представление идентификатора клиента;
- `native_language_code` - хранит код языка, который знает клиент;
- `learning_language_code` - хранит код языка, который клиент хочет выучить.

Для восстановления `WaitingUser` логически нужны три значения. Физически в элементе очереди хранится только `client_id`, а языковые коды выводятся из `key` направленной очереди.
После чтения из Redis значения не считаются валидными автоматически. Адаптер
последовательно восстанавливает их через `NewClientID`, `NewLanguage`,
`NewLanguagePair` и `NewWaitingUser`.

Для каждой языковой пары мы можем организовать свою очередь, это даст нам возможность получать коды языков прямо из ключа очереди.
Ключи могут быть такого формата:
`matchmaking:queue:{native_language}:{learning_language}`.

Примеры ключей:
`matchmaking:queue:ru:en`
`matchmaking:queue:en:ru`

А внутри самой очереди будут хранится только лишь `client_id`.

Порядок ожидания не является полем `WaitingUser`: он хранится положением `client_id` внутри упорядоченной структуры `Redis`.

Мы не будем сохранять ту же структуру полей, которую используем в domain-модели, потому что:
- закрытые поля domain-структуры не являются persistence-контрактом;
- внутреннее устройство Go-типа может измениться;
- данные должны восстанавливаться через конструкторы с повторной валидацией.

Имея только `ClientID`, метод `RemoveFromQueue` не знает key очереди. Поэтому потребуется обратный индекс:
`client_id` → направленная языковая пара или `key` очереди.

### 3.2. Ключи и структуры данных

| Key pattern | Redis type | Содержимое | Назначение |
|---|---|---|---|
| `fluent-swap:queue:{native}:{learning}` | LIST | `client_id` | Хранение и получение `client_id` в порядке очереди |
| `fluent-swap:queue:client:{client_id}` | STRING | key направленной очереди | По `ClientID` позволяет найти очередь клиента и назначить независимый TTL |

#### Очереди по языковому ключу

Структура `LIST` позволит нам класть идентификаторы в начало структуры и получать с конца списка. С ее помощью мы реализуем логику очереди. Вот пример подобного процесса с сайта официальной документации:
```
redis> LPUSH fluent-swap:queue:ru:en 3431-fdf-31345-drfgfgg
(integer) 1
redis> LPUSH fluent-swap:queue:ru:en 5432-fdw-24345-drfgllm
(integer) 2
redis> RPOP fluent-swap:queue:ru:en
"3431-fdf-31345-drfgfgg"
redis> RPOP fluent-swap:queue:ru:en
"5432-fdw-24345-drfgllm"
```

`LPUSH` - добавляет слева
`RPOP` - извлекает справа

Для удаления из структуры `LIST` можно будет воспользоваться функцией `LREM`:
```
LREM key count element — удаляет из списка элементы, равные значению element.count > 0: удаляет первые count вхождений от начала к концу.
count < 0: удаляет первые abs(count) вхождений от конца к началу.
count = 0: удаляет все вхождения элемента.

Пример: LREM fluent-swap:queue:ru:en 0 "3431-fdf-31345-drfgfgg" (удалит все строки "3431-fdf-31345-drfgfgg" из списка fluent-swap:queue:ru:en).
```

Почему `LIST`?
- `LIST` естественно сохраняет порядок;
- операции на концах эффективны;
- `LREM` для произвольного удаления имеет линейную сложность;
- `LIST` самостоятельно не обеспечивает уникальность;
- для ожидаемого размера очереди V1 этот компромисс принимается.

`ZSET` позволяет эффективно удалять произвольного пользователя и обеспечивает уникальность member внутри одной очереди, но требует отдельно формировать score для FIFO. Для небольших очередей V1 выбран более простой `LIST`, несмотря на линейную сложность `LREM`.

#### Обратный индекс клиентов

Отдельный `STRING` key на каждого клиента используется как обратный индекс. Его
значением является Redis key очереди, в которой находится клиент.

Пример:

```text
SET fluent-swap:queue:client:client-123 fluent-swap:queue:ru:en EX <ttl-seconds>
GET fluent-swap:queue:client:client-123
fluent-swap:queue:ru:en
```

Индекс позволяет различить отсутствие поиска, идемпотентный повтор в той же
очереди и конфликт с другой языковой парой. Отдельный key выбран вместо общего
`HASH`, потому что Redis может назначить ему независимый TTL. Компромисс —
большее количество keys.

Сам индекс не обеспечивает согласованность. Изменение `LIST` и client-key должно
выполняться одной атомарной операцией. Иначе клиент может остаться только в одной
из двух структур.

### 3.3. FIFO и поиск совместимой пары

`Redis key` зеркальной очереди строится по следующему принципу:

- Ключ текущей очереди: fluent-swap:queue:{native}:{learning}
- Ключ зеркальной очереди: fluent-swap:queue:{learning}:{native}

Самый ранний партнер извлекается командой `RPOP` с конца списка, так как внесение в структуру данных происходит с начала списка командой `LPUSH`.

Если зеркальная очередь пуста, входящий пользователь добавляется в очередь своей языковой пары, а `repository` возвращает `MatchResult{Matched: false}`.

Сортировка на стороне Go-приложения не понадобится, так как в Redis мы уже используем FIFO.

`LREM` удаляет конкретного клиента, но сохраняет взаимный порядок остальных элементов, поэтому `FIFO` для оставшихся пользователей не нарушается.

## 4. Семантика MatchOrEnqueue

### 4.1. Возможные результаты

| Исходное состояние | Действие | Результат repository | Итоговое состояние |
|---|---|---|---|
| `ClientID` отсутствует, совместимого партнёра нет | Добавление текущего клиента в левый конец собственной направленной очереди и создание записи в обратном индексе | `MatchResult{ Matched: false }`, `nil` | `ClientID` присутствует в своей `LIST` как самый новый элемент, а client-key содержит Redis key этой очереди |
| `ClientID` отсутствует, партнёр найден | Удаление партнера из очереди, удаление из индекса | `MatchResult{ Matched: true, Partner: WaitingUser{...} }`, `nil` | `ClientID` отсутствует в очереди и индексе, как и `ClientID` партнера |
| `ClientID` уже ожидает с той же `LanguagePair` | Ничего не происходит | `MatchResult{ Matched: false }`, `nil` | `ClientID` ожидает с той же `LanguagePair` |
| `ClientID` уже ожидает с другой `LanguagePair` | Ничего не происходит на уровне репозитория, но возвращается ошибка | `MatchResult{ Matched: false }`, `matchmakingservice.ErrClientAlreadyQueued` | `ClientID` остаётся в исходной очереди с прежней `LanguagePair`; его позиция и запись индекса не изменяются |

### 4.2. Граница атомарности

`MatchOrEnqueue` является одной бизнес-операцией, хотя затрагивает несколько
элементов Redis. В одну атомарную границу должны входить следующие действия:

1. Проверить обратный индекс входящего `ClientID`.
2. Если клиент уже находится в той же очереди, вернуть идемпотентный результат,
   не меняя его позицию.
3. Если клиент находится в другой очереди, вернуть
   `ErrClientAlreadyQueued`, не меняя состояние.
4. Извлечь самого раннего пользователя из зеркальной очереди.
5. Если партнёр найден, удалить его запись из обратного индекса и вернуть
   данные для восстановления `WaitingUser`.
6. Если партнёра нет, добавить входящего клиента в собственную очередь и
   создать запись в обратном индексе.

Атомарность отдельных Redis-команд не обеспечивает атомарность этого перехода.
После `LPUSH`, но до создания индекса, клиент уже находится в очереди, однако
`RemoveFromQueue` не сможет найти её по `ClientID`. Обратный порядок создаёт
противоположную рассинхронизацию: индекс существует, а элемента очереди ещё нет.
Аналогично, `RPOP` партнёра без удаления его индекса оставляет устаревшую запись.

Для реализации выбран Lua script, выполняемый Redis. Он позволяет выполнить
условные проверки и изменения очереди и индекса на стороне сервера как одну
неделимую операцию. Другой клиент Redis увидит состояние только до или после
скрипта, но не промежуточный результат.

`WATCH` вместе с `MULTI/EXEC` также может обеспечить optimistic concurrency, но
при изменении наблюдаемых keys транзакция отменяется, а приложение должно
повторить попытку. Для короткой операции с несколькими условными ветками Lua
выражает алгоритм прямее и не требует дополнительных сетевых round trips.

Lua script не должен выполнять сетевые вызовы или создавать комнату. Его граница
заканчивается формированием результата matchmaking. Создание комнаты и отправка
WebSocket-сообщений остаются последующими application/transport-операциями.

## 5. Семантика RemoveFromQueue

`RemoveFromQueue` получает только `ClientID`, поэтому сначала читает обратный
индекс и определяет key направленной очереди. Затем операция:

1. удаляет все вхождения `ClientID` из найденной очереди через `LREM ... 0`;
2. удаляет запись клиента из обратного индекса;
3. возвращает успешный результат.

Удаление из очереди и индекса должно быть атомарным: завершённая операция не
должна оставлять только одну из двух связанных записей.

Если клиента нет в обратном индексе, операция ничего не изменяет и завершается
успешно. Поэтому повторный `RemoveFromQueue` идемпотентен. Если индекс существует,
но элемента в очереди нет, операция удаляет устаревший индекс и также завершается
успешно. Это выполняет best-effort repair уже нарушенной согласованности, хотя
штатный атомарный алгоритм не должен создавать такое состояние.

## 6. TTL и очистка

Waiting-state должен иметь ограниченное время жизни, чтобы аварийно завершившийся
backend или потерянный disconnect не оставил клиента в очереди навсегда. TTL
начинается при успешной постановке в очередь и может продлеваться heartbeat или
явной операцией продления поиска. Конкретная длительность является конфигурацией,
а не domain-константой.

Первоначально рассмотренный общий `HASH` имеет критичное ограничение: Redis
назначает TTL всему key, а не отдельному hash field. `LIST` также не поддерживает
TTL отдельного элемента. Если устанавливать TTL всему индексу или языковой
очереди, один активный клиент будет продлевать жизнь устаревших записей либо
истечение key удалит сразу нескольких ещё активных клиентов.

Поэтому итоговая модель использует отдельный client-key вместо общего `HASH`:

```text
fluent-swap:queue:{native}:{learning}       LIST
fluent-swap:queue:client:{client_id}        STRING с per-client TTL
```

Значением client-key остаётся key направленной очереди. При постановке клиента
Lua script атомарно выполняет `LPUSH` и `SET ... EX`. При heartbeat TTL
продлевается только для конкретного client-key.

Истечение client-key не может автоматически удалить элемент из `LIST`.
Следовательно, очередь может временно содержать stale `ClientID`. При выборе
партнёра Lua script должен проверять существование его client-key и пропускать
просроченные элементы, пока не найдёт живого партнёра или не опустошит очередь.
Это lazy cleanup. Явный `RemoveFromQueue` по-прежнему удаляет обе записи сразу.

Количество stale элементов, удаляемых одним script, должно быть ограничено:
длинный Lua script блокирует обработку других команд Redis. Если лимит очистки
исчерпан, операция не продолжает неограниченный цикл, а ставит входящего клиента
в очередь и завершает вызов без match. Следующие обращения продолжат cleanup.

Ограничение стратегии: stale элементы занимают память и удаляются только при
обращении к соответствующей языковой очереди. Для V1 это приемлемо при
ограниченном TTL и мониторинге длины очередей. Если очереди станут большими или
редко используемыми, понадобится периодическая очистка либо другая модель,
например `ZSET` с временем истечения в score.

## 7. Ошибки и context cancellation

- Если `context` отменён до обращения к Redis, repository возвращает
  `ctx.Err()` и не вызывает зависимость.
- Если `context` отменён во время сетевого вызова, repository возвращает ошибку
  клиента Redis с сохранением причины. Нельзя утверждать, что состояние не
  изменилось: сервер мог завершить Lua script до разрыва соединения.
- Если Redis недоступен, matchmaking завершается внутренней ошибкой. Переход на
  локальный memory fallback запрещён, потому что он создаст независимую очередь
  и нарушит single-match invariant при нескольких backend-инстансах.
- Повреждённый ответ Redis нельзя передавать в application layer как валидный
  `WaitingUser`; adapter должен вернуть внутреннюю ошибку.

Повтор запроса после неопределённого результата безопасен только частично. Если
первый вызов успел поставить клиента в очередь, обратный индекс обеспечивает
идемпотентный повтор без изменения позиции. Если первый вызов успел создать
match и удалить waiting-state, текущий контракт `MatchOrEnqueue(ClientID,
LanguagePair)` не позволяет отличить retry от нового поиска и вернуть прежний
результат.

Полная идемпотентность успешного match потребует operation/request ID и временной
записи результата либо более широкой координации с созданием комнаты. Это не
следует скрывать внутри Redis adapter и не входит в первый подэтап реализации.

## 8. Конкурентные сценарии

### 8.1. Два backend-инстанса выбирают одного партнёра

Пусть `partner-X` первым ожидает в очереди `en:ru`, а два backend-инстанса
одновременно обрабатывают новых клиентов с парой `ru:en`.

Если алгоритм сначала читает партнёра, а затем удаляет его отдельной командой,
возможен следующий interleaving:

| Шаг | backend-1 | backend-2 | Redis state |
|---:|---|---|---|
| 1 | читает `partner-X` | | `partner-X` ещё в очереди |
| 2 | | читает `partner-X` | `partner-X` ещё в очереди |
| 3 | удаляет `partner-X` | | очередь пуста |
| 4 | | пытается удалить `partner-X` | очередь пуста |
| 5 | возвращает match | возвращает match | один партнёр выдан дважды |

В выбранной модели партнёр извлекается через `RPOP`, поэтому уже одна эта
команда не выдаст элемент дважды. Lua script расширяет атомарную границу:
извлечение партнёра и удаление его client-key наблюдаются как одна операция.
Пока выполняется первый script, второй не может начать собственную операцию.
После завершения первого script второй увидит пустую очередь и поставит своего
клиента в ожидание. Инвариант single-match сохраняется.

### 8.2. Один ClientID отправляет два одновременных запроса

Lua scripts выполняются Redis последовательно, поэтому один из двух запросов
обязательно станет первым.

Для одинаковой `LanguagePair` первый script либо создаёт match, либо ставит
клиента в очередь. Если клиент был поставлен в очередь, второй script находит
его client-key, возвращает `MatchResult{Matched: false}` и не выполняет повторный
`LPUSH`. В очереди остаётся ровно одно вхождение, а FIFO-позиция не меняется.

Если одновременные запросы содержат разные `LanguagePair` и первый поставил
клиента в очередь, второй находит client-key с другим queue key, возвращает
`ErrClientAlreadyQueued` и не меняет состояние. Клиент остаётся только в очереди,
выбранной первым завершившимся script.

Если первый запрос сразу создал match, waiting-state клиента отсутствует и
второй запрос может быть воспринят как новый поиск. Это тот же открытый вопрос
идемпотентности успешного результата, описанный в разделе 7; одного `ClientID`
для его решения недостаточно.

## 9. Рассмотренные альтернативы

### `ZSET` вместо `LIST`

`ZSET` обеспечивает уникальность member внутри одной очереди, эффективное
произвольное удаление и выбор минимального score. Для FIFO пришлось бы выбрать
монотонный score и определить разрешение коллизий. Кроме того, один `ClientID`
всё ещё мог бы присутствовать в разных языковых `ZSET`, поэтому глобальный
обратный индекс остался бы необходим. Для небольших очередей V1 выбран более
простой `LIST` с осознанной стоимостью `LREM` и lazy cleanup.

### Общий `HASH` вместо per-client `STRING`

Общий `HASH` уменьшает количество Redis keys и удобно отображает `ClientID` в
queue key. Он отвергнут после анализа TTL: отдельному hash field нельзя назначить
независимое время жизни. Per-client `STRING` увеличивает количество keys, но даёт
независимый TTL и сохраняет быстрый поиск очереди по `ClientID`.

### `WATCH` и `MULTI/EXEC` вместо Lua

Optimistic transaction потребовала бы наблюдать изменяемые keys, обрабатывать
конфликт `EXEC` и повторять операцию. Lua лучше соответствует короткому
условному переходу состояния, который целиком исполняется Redis.

### Distributed lock

Отдельный distributed lock не нужен. Одна серверная атомарная операция уже
сериализует конфликтующие изменения. Lock добавил бы новый key, TTL lock-а,
обработку истечения и владения lock-ом, не решая дополнительной задачи.

## 10. Открытые вопросы

- Нужна ли полная идемпотентность успешного match после потери ответа и должен ли
  внешний контракт получить operation/request ID?
- Как связать атомарный результат matchmaking с последующим созданием комнаты,
  чтобы сбой между этими шагами не потерял найденную пару?
- Какой TTL поиска и интервал heartbeat выбрать после появления требований к
  клиентскому lifecycle?
- Нужна ли фоновая очистка stale элементов `LIST` или lazy cleanup достаточно
  для ожидаемой нагрузки V1?
- При переходе на Redis Cluster все keys одного Lua script должны попадать в один
  hash slot и передаваться script явно. Client-key партнёра определяется только
  после `RPOP`, поэтому одного общего hash tag может оказаться недостаточно:
  потребуется отдельно пересмотреть key model и границу script.
